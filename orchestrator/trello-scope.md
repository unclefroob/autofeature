# Trello Scope — Fetch Card + Generate Technical Scope

Called by the main orchestrator when a `trello.com/c/` URL is detected in the feature request.

---

## Step 1: Check MCP Availability

Verify the Trello MCP tools are available in this session. Look for `mcp__trello__get_card` in the tool list.

If not available:
> ⚠️ Trello MCP server is not connected.
>
> To enable Trello integration, add to `~/.zshrc`:
> ```bash
> export TRELLO_API_KEY=your-key   # https://trello.com/app-key
> export TRELLO_TOKEN=your-token
> ```
> Then restart Claude Code. The MCP server is already registered.
>
> Continuing without Trello — using original prompt as feature request.

Return to orchestrator with `TRELLO_ACTIVE = false`. Orchestrator skips the rest of this file.

---

## Step 2: Extract Short Link

Parse the short link from the URL.

Examples:
- `https://trello.com/c/abc1DEF2/123-card-title` → `abc1DEF2`
- `https://trello.com/c/abc1DEF2` → `abc1DEF2`

Pattern: the path segment immediately after `/c/`.

---

## Step 3: Fetch Card Data

Call `mcp__trello__get_card` with `{ cardId: "<short link or card ID>", includeMarkdown: true }`.

Extract:
- `name` → card title
- `desc` → card description (may be empty)
- `labels` → array of label names (e.g. "bug", "enhancement", "backend")
- `due` → due date if set (note in brief, don't block on it)
- `url` → canonical card URL (for linking back in the scope comment)

If the card fetch fails (invalid ID, permission error):
> ⚠️ Could not fetch Trello card `[short link]`. Check that the card exists and your token has access.
>
> Continuing without Trello — using original prompt as feature request.

Return `TRELLO_ACTIVE = false`.

---

## Step 4: Fetch Acceptance Criteria

Call `mcp__trello__get_acceptance_criteria` with `{ cardId: "<card ID from Step 3>" }`.

Extract checklist items as a flat list of strings:
```
- [ ] Item text (incomplete)
- [x] Item text (complete)
```

These become the acceptance criteria in the Feature Brief.

If no "Acceptance Criteria" checklist exists on the card, skip silently.

---

## Step 5: Generate Technical Scope

Using the card name, description, labels, and checklist items — synthesise a technical scope analysis. Do NOT call any external tools for this step; reason from the card content and the current repo context already gathered by the orchestrator.

### Scope Tier
Apply the same classification logic as `scope-gate.md`:
- **micro**: single file or function change, no schema work, no cross-layer touches
- **single-layer**: one layer (API only, or frontend only, or DB only)
- **cross-stack**: touches API + frontend or API + mobile in the same repo
- **cross-repo**: requires changes across multiple repos

### Affected Layers
List which of these are touched: `API routes`, `controllers`, `middleware`, `DB schema`, `DB indexes`, `React frontend`, `React Native screens`, `auth flow`, `background jobs`, `external integrations`.

### Technical Breakdown
2–3 sentences: what needs to be built, which parts of the codebase are touched, key patterns to follow.

### Key Decisions Needed
List 1–3 non-obvious technical decisions the implementer will face (architecture choices, trade-offs, ambiguities in the card). If none, write "None — card is sufficiently specified."

### Risks / Unknowns
List concrete risks (e.g. "No migration plan for existing records", "Card doesn't specify error handling for X"). If none, write "None identified."

### Effort
Choose one: `XS` (< 1h) | `S` (1–4h) | `M` (half day) | `L` (1–2 days) | `XL` (> 2 days)

---

## Step 6: Format Scope Comment

Assemble the comment string:

```
🤖 **AutoFeature — Technical Scope**

**Scope Tier:** [tier]
**Affected Layers:** [comma-separated list]

**Technical Breakdown:**
[2–3 sentences]

**Key Decisions Needed:**
- [decision 1]
- [decision 2]

**Risks / Unknowns:**
- [risk or "None identified"]

**Effort:** [XS | S | M | L | XL]

---
*Generated by AutoFeature · [YYYY-MM-DD] · [card URL]*
```

---

## Step 7: Checkpoint — Show Preview + Options

Present to the user:

```
Trello Card: [card name]
[card URL]

Technical Scope Comment (preview):
──────────────────────────────────────
[scope comment]
──────────────────────────────────────

A) Post comment to Trello + use card as feature request  ← default
B) Post comment to Trello + use original prompt instead
C) Skip posting + use card as feature request
D) Skip Trello entirely — use original prompt
```

Wait for selection before continuing.

---

## Step 8: Post Comment (if A or B selected)

Call `mcp__trello__add_comment` with:
- `cardId`: card ID from Step 3
- `text`: scope comment from Step 6

If posting fails, warn but do not abort:
> ⚠️ Could not post Trello comment (API error). Continuing with card content as feature request.

---

## Step 9: Return to Orchestrator

Set the following for use in all downstream steps:

| Variable | Value |
|----------|-------|
| `TRELLO_ACTIVE` | `true` |
| `TRELLO_CARD_URL` | card URL |
| `FEATURE_REQUEST` | If A or C: card `name` + `desc` + checklist items formatted as acceptance criteria. If B or D: original prompt. |
| `TRELLO_SCOPE_TIER` | Scope tier from Step 5 (pre-fills Step 3 of main pipeline) |

**Feature request format (options A and C):**

```
[Card name]

[Card description]

Acceptance Criteria:
- [ ] [checklist item 1]
- [ ] [checklist item 2]
```

The orchestrator uses `FEATURE_REQUEST` as the input to Step 1 (Mode Selection) and Step 2 (Feature Interrogation) in place of the user's raw prompt.
